# Trustworthy local alpha contract

This release strengthens document recovery and query governance, adds section-aware canvas composition, and makes assistant edits reviewable. Native semantic-engine execution remains a later phase. An opt-in company workspace now adds authentication and operations; its separate [self-hosting contract](self-hosting.md) documents the boundaries.

## Document lifecycle

Every new canvas, suggestion or demo clears saved identity, undo history, selection and drill state after the recovery gate succeeds. Save only changes the status to Saved after a successful server response. Editing during an in-flight save remains dirty; navigating to another document prevents a late response from adopting the old ID. Save a copy offers a new identity when another tab or agent has changed the saved revision.

Document fingerprints include the spec and canvas settings. Cross-filters and drill state remain exploratory. Undo/redo covers tile edits, movement, keyboard nudges and canvas settings. Refresh invalidates the tile query context and cache key without regenerating tiles. A role change clears query and explanation state while preserving authored content.

Drill state belongs to the chart's metrics, grouping and authored filters. Changing any of those clears only that chart's drill before a new query is sent; removing the chart also discards its drill. Title, layout and formatting changes preserve exploration. Undoing a query edit restores the authored definition without reviving the old drill range. Drill state remains absent from saved dashboard versions.

Interactive category and time charts expose **Explore chart**, a keyboard-accessible disclosure with a native category or reporting-period selector and an explicit filter/drill action. Tab moves between controls; native type-ahead selects a value; Enter or Space activates the action; Escape closes the disclosure. Selection preserves original value types, and generated waterfall totals are not filter choices. Small-multiple panel labels retain their direct keyboard buttons. Daily buckets do not offer a deeper drill. Query redraws restore exploration focus unless the user has moved to another control. Exploration controls are excluded from PNG exports.

Design review is nonmodal: opening moves keyboard focus into the panel, while the canvas remains available for editing. Escape from the panel or its toolbar trigger closes review and returns focus to the trigger. Continuous rescans do not take focus away from the canvas. Keeping or applying a story structure returns focus to the preview control, or to the review panel when no further structure proposal remains.

The canvas assistant opens at its labeled message field. The field remains focusable but read-only while a request is pending, with a keyboard-accessible Stop action. Closing returns focus to the assistant toggle; applying or dismissing a proposal returns to the message field. Incoming replies do not move focus. Errors are announced, and reopening preserves the unsent message within the same conversation.

Pointer movement and resizing belong to the pointer that started the gesture. Escape, pointer cancellation, unexpected capture loss, window blur or locking the canvas restores the unfinished gesture's geometry without adding an undo step. Restoration preserves concurrent content edits and does not recreate removed tiles. A completed geometry change creates one undo step; fractional click jitter or returning to the original geometry does not. Shift-click adds/removes items without collapsing the remaining selection, grouped movement keeps pinned items fixed, and moving a chart never snaps its existing width or height to a new size.

The persistent mode bar distinguishes Edit, Preview and Viewer access. Preview is transient UI state; it does not dirty or publish the document. Each successful save records an immutable design version in the source-scoped dashboard store. Version history previews saved layouts and restores a selected version as an unsaved draft, retaining the current draft in recovery. The next save creates a new revision. History is included in library backups and removed when its dashboard is deleted. It does not freeze query results or semantic metric definitions, and cannot recover revisions overwritten before history was installed.

Version-history list and preview failures have independent retry controls. Empty history is an explicit state. Preview responses must match the requested dashboard and revision and pass the shared document schema before restoration becomes available. Changing the selection clears the prior preview immediately; aborted or late responses cannot replace the selected version. Failed reads leave the current dashboard untouched.

The restore comparison reads from current work (including unsaved edits) to the selected saved version. It separates data/scope, story/content and layout/appearance changes across all tabs. Data changes include metric references, time grains, chart filters, shared defaults, limits and comparison baselines; they do not compare warehouse values or historical metric definitions. Temporary cross-filters and preview locking are excluded, matching the save contract. Object property ordering does not count as a change, while authored array order is retained. Image changes are identified without printing embedded image payloads.

Save and rename timestamps are explicit UTC values shared by the library and version history, displayed in the viewer's local time zone. Legacy timestamps are recovered only from matching version-history evidence; otherwise their time zone remains unknown. Format-2 backups preserve that distinction through restore on a machine in another time zone, while still accepting format-1 archives. See the [backup compatibility contract](self-hosting.md#back-up-restore-and-upgrade).

A browser draft is written after edits and immediately before navigation. Home offers recovery and explicit discard. Recovery records are validated. Failed recovery writes block document replacement and offer a downloadable JSON backup or explicit discard. Home can import a compatible backup as a new unsaved document after validating its source and contents. Recovery is local to a browser origin, is subject to its quota, and is not a backup of the server database. Save errors and unavailable recovery storage remain visible.

Smart Arrange previews section-aware layouts before applying tiles and canvas dimensions as one undo step. A pinned tile anchors its section during arrangement. Assistant proposals receive the current unsaved document, validate all actions before application, and are rejected if the document has changed since the request. Applying a proposal does not save it automatically.

Assistant chart edits support the full persisted visualization library. New charts and changed encodings are checked against the renderer's supported dimension/measure shapes and unit rules after all proposal actions have been combined. This lets a chart choice and its query change arrive in either order. Invalid combinations reject the entire proposal, including accompanying title or layout edits. Layout-only recovery can retain an unchanged chart error. Structural validity does not verify geographic values, funnel semantics, source quality or factual claims; result checks and review remain necessary.

AI redesign checks the proposed queries and charts before application. New failures and failures on charts whose query, encoding, formatting or size changes remain blocking. A chart with the same observed error in the current dashboard can be retained only when those properties and its effective filter/drill scope are unchanged; the preview names the remaining problem and requires explicit acknowledgment. Position, section and title changes alone do not imply that the underlying issue is repaired. Retrying checks or generating another proposal clears acknowledgment. Text-only layouts disclose that there are no chart queries to check instead of waiting indefinitely. One undo restores the complete prior design.

Assistant clarification answers remain in the open page until the server acknowledges them. Failed submissions show an error and a retry action without clearing the question or typed response. Failed background refreshes preserve the pending question; polling pauses during submission, and acknowledged questions cannot reappear from stale list responses. This is in-page recovery, not persistent storage across a reload.

Closing a chart explanation or AI suggestions panel, changing its query context, or removing the tile cancels its pending browser request. The API forwards cancellation to the provider request and tool HTTP calls; cancelled requests cannot start another tool or return a late answer. A new request can be made after cancellation. This does not roll back completed work or interrupt a warehouse query that has already started. Cancellation is covered with a local fake provider; it does not establish provider-side billing behavior.

## API changes

Dashboard tabs may contain an optional `brief` with authored `question`, `takeaway`, `nextStep` and optional `evidenceIds` for infographic selection. Save/restore retains it; tab copying remaps its chart references. Omitting `evidenceIds` means all current charts, while an empty array means no selection. Missing references remain visible for the author to resolve rather than silently selecting a different chart. These notes do not alter queries or certify business conclusions. See [presentation behavior](presentations.md).

- `POST /api/dashboards`: validates `id`, `spec`, `canvas`, `schemaVersion` (currently 1) and `revision`. Default revision 0 means create only. A successful response includes the new revision. Conflicts return 409.
- Dashboard list/get/save/delete/arrange are scoped to the selected source ID, including when two models have the same display name. An explicitly unavailable source returns 404.
- Delete requires the current revision. Arrange respects the requested named layout and checks the loaded revision before writing.
- Query bodies contain metrics, dimensions, structured filters, comparison and a bounded limit; arbitrary query properties and raw SQL filters are rejected. Saved tile geometry must be finite and positive, with unique IDs.
- Chart queries and discovery endpoints deny unenforceable policies with 403. The configured RLS file must exist and be structurally valid; explicit `policies: []` disables policies for an intentionally unrestricted local installation.
- Local mode binds to loopback and checks Host/Origin headers; its role selector is a simulation. Company mode requires HTTPS/OIDC, explicit access rules and server-side sessions. The browser cannot select a different row principal. See the self-hosting guide for deployment and session limits.
- The workspace mounts only after a validated session response. Pending, signed-out and malformed responses do not start protected API requests. Gateway renewal can refresh tokens for the same account and access scope; an account, role or row-policy change closes the mounted workspace and requires sign-in again. Unsaved work is stashed under the original account before closing. Browser regressions cover these transitions with synthetic sessions; the server remains responsible for enforcing authorization on every request.

## Query semantics

One tile uses one base table. Dimensions and filters must be reachable through one unambiguous declared relationship. Composite keys are compiled as a conjunction and inner/left join types are preserved. Join cardinality and referential integrity still depend on the authored model; there is no general fanout-proof metric planner.

Simple dbt imports accept column-based sum, count, count-distinct, min, max and average measures. `COUNT(1)` is supported. Complex expressions, measure parameters, non-additive dimensions and metric filters are rejected. File import is a deliberately restricted subset, not native MetricFlow execution.

Snowflake import preserves database/schema/table identity and all keys in an equality relationship. Unsupported computed fields, named/entity filters, non-additive dimensions, private access, variables, explicit metric join paths, SQL-defined tables, range/asof relationships and top-level metrics reject the source. These properties affect execution or visibility in the [Snowflake YAML specification](https://docs.snowflake.com/en/user-guide/views-semantic/semantic-view-yaml-spec); this adapter does not silently discard them. SQL expressions inside a supported model remain trusted administrator input, not an untrusted SQL sandbox. Reusing a physical table name for multiple logical aliases is rejected. Logical table names and per-table field names must be unambiguous; metric names must be unique across the imported model. Unsupported identifiers and case-only collisions fail loading instead of overwriting an earlier definition. Bare fact references resolve without case-sensitive misses, including when several differently named facts or a dimension share their physical column, without rewriting SQL literals/comments or repeatedly qualifying an earlier replacement.

Connected tables, Modeler extensions and duckglue files retain an authored `default_date_column` as a default trend axis. It must identify a date or timestamp column on that table. It neither creates a physical partition nor certifies period coverage; explicit native-period metadata remains separate.

Period-over-period SQL matches the previous calendar bucket; missing matches produce NULL. Year-over-year uses calendar-year subtraction; a leap-day comparison clamps to February 28 in the prior year. Weekly year-over-year matches a date one calendar year earlier, not an ISO week-number convention; when there is no matching bucket, it stays unknown. The model can declare a Sunday/Monday week start, fiscal year start month, and reporting time zone (see [Calendar](calendar.md)). Retail 4-4-5 calendars, dense date-spine filling, and automatic missing-to-zero conversion are not implemented.

Time queries retain the newest bounded window and return it in chronological order. The server fetches one additional row to detect truncation, then removes that probe and returns the visible window, limit and warnings. Limited charts and exports are labeled. Upstream period completeness remains unknown; fitting all query rows into a response does not establish complete source coverage. KPI cards select their named metric and latest non-null time bucket. Null latest metric values remain unknown, and sparse prior periods are not silently substituted with an older observation.

Metric authors may declare supported time grains and a required time dimension. The included snapshot and retention metrics require monthly grouping; unsupported coarsening and all-time totals are rejected. This restriction prevents unsafe aggregation but does not implement generic snapshot rollups. KPI change colors follow declared metric direction, with unknown direction shown neutrally.

Duckglue tables may declare `period: { column, grain }` for whole-period summary rows. Coverage follows that declared period at coarser compatible grains; date primary keys alone do not suppress edge checks. Comparisons never use an excluded partial edge as their baseline. These are reporting semantics and observed-result checks, not a certification that all warehouse data has arrived. See [reporting periods](calendar.md#declaring-what-period-a-source-row-represents).

Metrics with different always-on filters aggregate separately and merge dimension keys null-safely. Metric filters select the finished values after those groups are merged, computed metrics are evaluated, and period comparisons are attached, but before the result limit. Filtering displayed values therefore does not remove earlier periods from a running total or its prior-period lookup. Dimension/date filters and row policies still restrict the input rows before aggregation.

Chart suggestions, default chart inference and rendering share structural capability checks. Time plus one category supports a line per category, stacked area, heatmap or small multiples for one measure. Two categorical breakdowns support a heatmap or stacked bars. Additional measures with two breakdowns, or more than two breakdowns, default to a table rather than dropping fields. Explicit unsupported choices show an error and cannot be exported as a ready chart, including KPI cards that would omit selected fields.

Category trends use the model's time-field declaration, preserve category identity and align the observed periods across series. Missing category/period pairs remain gaps; this is not a complete calendar spine or evidence that absent values are zero. Duplicate category/period rows require inspection rather than automatic aggregation. Stacked areas and bars reject missing components because their total would be unknown. These structural checks do not establish that selected metrics are additive or suitable parts of a whole.

## Storage and migration

The dashboard store uses an additive migration for source ID, schema version and revision. Old document JSON is retained. Old text-size presets normalize to numeric sizes on read. A unique model-name-to-source mapping attaches legacy records; ambiguous matches remain unassigned and preserved. Section membership and pinned positions are optional tile fields. Older documents infer sections from heading positions when arranged. An explicit `section: null` keeps a loose tile outside sections even after it moves past a heading; older app versions may reject this value or the new fields.

Smart Arrange keeps individual pins fixed on a loose canvas and packs other tiles through the available space. A pin within an authored heading section protects that whole section, including its reading space. Layout preview reports how many tiles move or resize and explains when everything is pinned or the proposed layout is already in place. Unchanged layouts cannot be applied. Arrangement changes geometry and explicit section membership, not metric definitions, queries, filters or authored text; one undo restores the previous document.

DuckDB connections serialize store operations. Saves validate first, check source/revision, and replace a row inside a transaction. The DuckDB client is pinned to 1.5.5-r.4; its predecessor was an early alpha and failed the new update regression. Explicit transactional replacement also avoids indexed-update limitations described in [DuckDB's index documentation](https://duckdb.org/docs/current/sql/indexes.html#constraint-checking-in-update-statements).

Stop the old server and copy its dashboard directory before upgrading. Do not share a dashboard file between two running app processes. For an isolated trial, set `SC_DATA_DIR` to a new directory. Recovery of ambiguous legacy records currently requires an administrator to assign the intended `source_id` after inspecting a backup.

## Validation scope

Field profiling accepts at most 12 fields per request, deduplicates repeated names, and validates the whole batch against the model and access scope before querying. Each profiling query has a three-second deadline, including waiting for a connection; the whole field batch has a fifteen-second cancellation deadline. Client disconnects also cancel queued and running profiling work. DuckDB interrupts the leased connection. Snowflake sends a statement cancellation request and per-statement execution/queue timeout parameters; cancellation is best effort and the connector retains its lease until the driver confirms completion. These are execution safeguards, not a guarantee of scanned bytes, warehouse cost or a strict HTTP response-time ceiling during network failure. Exact distinct counts can still scan the scoped relation within the deadline.

Missing, malformed, timed-out or contradictory counts remain unknown rather than becoming zero or an estimated exact count. Count and sample evidence can fail independently, preserving the evidence that succeeded and returning an explicit warning. Chart review marks those checks incomplete and offers a retry. The tile picker and inspector display the limitation while still allowing a person to choose a visualization. Real local DuckDB interruption/reuse is regression-tested; Snowflake cancellation and timeout parameters are covered with a simulated driver, not a live warehouse acceptance test.

Tests cover the sample warehouse, exact synthetic DuckDB answers, source isolation, concurrent revisions, old store schema migration, malformed policy/config input, rejected adapter semantics, agent tool context and tool-schema serialization. Additional fixtures verify latest-window comparisons, native-grain restrictions, atomic proposals, pinned sections, retired pool drainage and the Snowflake SDK's TOML parser interface. Browser regressions exercise save/new/open, refresh and role changes, failed save retry, recovery failure, backup import, keyboard editing, layout preview/undo, partial design reviews and mocked assistant proposal flows.

Live Snowflake and compatibility with arbitrary vendor manifests need integration testing with real credentials and fixtures. A synthetic live AI redesign has produced a validated proposal, but factual narrative quality and repeatability remain acceptance work. Replaced connection pools reject queued/new work, drain active leases and close retired connections. DuckDB partial initialization failures are regression-tested; Snowflake tests verify cleanup attempts after partial initialization with a simulated SDK. Actual remote-session cleanup and warehouse timeout behavior still need live verification. The profiling cancellation/deadline support described above is implemented; general warehouse-wide execution and cost budgets are not. Distributed sessions, document-level permissions, general asset storage, source deletion ownership and responsive published dashboards remain outside this release. Local browser tests and prepared demo animations do not establish production readiness.
